# Правила работы Codex

Эти правила обязательны для всех задач Codex в этом репозитории.

## Главный принцип

Ограничиваем не технические инструменты, а объём разработки.

Codex может использовать обычные средства разработки, которые нужны для выполнения утверждённой задачи: package manager, документацию, shell, временную среду, проверки, сборку и локальный dev-сервер.

Но кодить разрешено только то, что прямо входит в текущую Issue.

Если действие техническое и нужно, чтобы выполнить уже поставленную задачу, отдельное разрешение не требуется.

Если появляется новая функция, рефакторинг, архитектурное улучшение или работа «на будущее», которых нет в Issue, это делать нельзя.

## Язык общения

- Общайся с пользователем на русском языке.
- План, промежуточные сообщения и итоговый отчёт пиши на русском.
- Текст интерфейса меняй только по требованиям конкретной задачи.

## Scope

1. Реализуй только явно поставленную задачу.
2. Не расширяй продуктовый scope.
3. Не реализуй будущие функции.
4. Не делай ничего «заодно».
5. Не переделывай несвязанный интерфейс.
6. Не рефактори несвязанный код.
7. Не меняй архитектуру без отдельной задачи или явного разрешения.
8. Если заметил улучшение, запиши его в отчёт, но не реализуй.

## Перед началом работы

Перед изменениями:

1. Прочитай:
   - README.md
   - MVP.md
   - ARCHITECTURE.md
   - CODEX_RULES.md
   - текущую GitHub Issue.
2. Коротко напиши:
   - что именно собираешься сделать;
   - какие основные файлы ожидаешь создать или изменить;
   - какие зависимости нужны.
3. Проверь, что каждый пункт плана нужен именно для текущей Issue.

Не останавливай работу только из-за обычных технических действий, необходимых для текущей задачи.

## Файлы и зависимости

- Создавай и изменяй только файлы, реально необходимые для текущей задачи.
- Можно создавать стандартные технические файлы фреймворка, если они нужны для запуска текущей задачи.
- Не меняй проектную документацию, если этого не требует Issue.
- Не добавляй зависимости, которые не используются текущей задачей.
- Не обновляй зависимости без необходимости.
- Не добавляй UI-kit, state manager, database, auth, analytics и другую инфраструктуру без соответствующей задачи.

## Изменения

- Предпочитай минимальный diff.
- Сохраняй рабочее поведение вне текущей задачи.
- Не делай попутную чистку.
- Не переименовывай несвязанные компоненты, маршруты и переменные.
- Если задачу можно решить просто, не усложняй архитектуру «на будущее».

## Git

- Одна задача = один небольшой проверяемый commit максимум.
- Не объединяй несколько функций или несвязанных исправлений.
- Не создавай PR, не merge и не закрывай Issue самостоятельно, если это не указано в задаче.
- Не переписывай git history без отдельного запроса.

## Проверка

После завершения задачи выполни применимые проверки:

- lint;
- typecheck;
- tests, если есть;
- production build.

Если задача создаёт или меняет UI, запусти приложение для ручной проверки.

Для dev-сервера по умолчанию используй порт 3100, если он свободен. Если занят, используй другой свободный порт и явно сообщи его.

Если сервер недоступен пользователю извне среды выполнения, честно сообщи это.

## Итоговый отчёт

В конце каждой задачи напиши:

1. какие файлы созданы и изменены;
2. что именно реализовано;
3. какие зависимости добавлены;
4. результаты lint/typecheck/tests/build;
5. адрес приложения для ручного теста, если доступен;
6. замеченные несвязанные проблемы, которые ты не исправлял.

После этого остановись.

Не переходи к следующей функции без явного разрешения.
